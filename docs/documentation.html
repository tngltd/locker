Lock-Down Service

Android-based service lockdown for Ubuntu systems

User Guide

Locker protects your Ubuntu server by tying service availability to a physical Android device. When your device is connected, services run normally. When it's disconnected, Locker stops the configured services — and keeps them stopped, even if someone tries to restart them manually.

Installation

Install from .deb Package

sudo apt install -y ./locker_1.0.0-1_all.deb

After installation the service starts automatically in permissive mode (monitoring only, no enforcement).

Verify Installation

# Check if the package is installed
dpkg -l | grep locker

# Verify the service is running
sudo systemctl status locker

# Test the CLI
locker --help

Quick Start

Four steps to protect your services:

Step 1: Connect and Identify Your Android Device

Connect your Android device via USB (with USB debugging enabled) and list connected devices:

locker list-devices

Then set the device serial:

# Auto-detect from connected devices
sudo locker set-android-serial

# Or set a specific serial directly
sudo locker set-android-serial ABC123XYZ

Verify it's configured:

locker get-android-serial

Step 2: Add Services to Protect

Tell Locker which services to manage. These will be stopped when the device is disconnected and started when it reconnects:

sudo locker add-service ssh
sudo locker add-service nginx
sudo locker add-service cron

View configured services and their current status:

locker list-services

Step 3: Switch to Enforcing Mode

Important: Make sure your Android device is connected before switching to enforcing mode, otherwise Locker will immediately stop the configured services. 
sudo locker set-mode enforcing

Step 4: Verify

Disconnect your Android device and watch the configured services stop. Reconnect it and they start again.

CLI Command Reference

Command Description Requires sudo
locker list-devices List connected Android devices with serial numbers No
locker get-android-serial Show the currently configured Android serial No
locker set-android-serial [serial] Set the Android device serial (interactive if no serial given) Yes
locker add-service <name> Add a service to be managed by Locker Yes
locker remove-service <name> Remove a service from Locker's management Yes
locker list-services List all managed services with their current status (RUNNING/STOPPED) No
locker set-mode [permissive|enforcing] Set the operating mode (interactive if no mode given) Yes
locker logs [-n N] [-f] Show audit log (last N lines, default 50). Use -f to follow in real time No

Modes

Permissive Mode (default)

  • Locker monitors the device connection but does not stop or start any services
  • Safe for initial configuration and testing
  • All actions are logged for audit purposes

Enforcing Mode

  • Locker actively stops managed services when the Android device is disconnected
  • Locker automatically starts managed services when the device reconnects
  • Services that are manually started while the device is disconnected will be stopped again on the next check cycle (every 5 seconds by default)
  • Requires an Android serial to be configured

Audit Logging

All operations are logged to /var/log/locker.log, including:

  • Service lock/unlock operations by the daemon
  • Device connection status changes
  • All CLI commands and their output
  • Configuration changes

View the log:

# Show last 50 lines
locker logs

# Show last 100 lines
locker logs -n 100

# Follow the log in real time (like tail -f)
locker logs -f

Testing Without a Physical Device

For demos or testing, you can simulate a connected device using the connected serials file. Create a JSON file at /etc/locker/connect_android_serials.json with the matching serial:

# Simulate device connection
sudo bash -c 'echo '"'"'{"android_serial": "YOUR_SERIAL_HERE"}'"'"' > /etc/locker/connect_android_serials.json'

# Simulate device disconnection
sudo rm /etc/locker/connect_android_serials.json

The service checks this file as a fallback when no real USB device is detected. If the serial in the file matches the configured serial, the device is treated as connected.

Tip: An interactive end-to-end demo is included. Run make demo from the project root to see Locker in action with a simulated device.

Configuration File

The configuration is stored in /etc/locker/config.json:

{
  "service": {
    "log_level": "INFO",
    "log_file": "/var/log/locker.log"
  },
  "monitoring": {
    "check_interval_seconds": 5
  },
  "mode": "permissive",
  "android_serial": "ABC123XYZ",
  "services": ["ssh", "nginx"]
}

Do not edit this file directly — use the CLI commands to make changes. The service re-reads the configuration on every monitoring cycle.

Service Management

# Start the service
sudo systemctl start locker

# Stop the service
sudo systemctl stop locker

# Restart the service
sudo systemctl restart locker

# Check status
sudo systemctl status locker

# View systemd journal logs
sudo journalctl -u locker -f

Uninstallation

sudo systemctl stop locker
sudo apt remove locker

This removes the package, the log file, and the logrotate configuration. Configuration files in /etc/locker/ are preserved unless you run apt purge locker.

Troubleshooting

Service Not Starting

sudo systemctl status locker
sudo journalctl -u locker -n 50

Common causes: missing config file, invalid JSON in config, or permission issues. Try rebuilding and reinstalling with make install.

Device Not Detected

  • Ensure USB debugging is enabled on the Android device
  • Check that pyudev is installed: python3 -c "import pyudev"
  • Verify the device appears in locker list-devices

CLI Commands Not Writing to Log

The log file at /var/log/locker.log must be writable by both root (service) and your user (CLI). Check permissions:

ls -la /var/log/locker.log
# Should be -rw-rw-rw- (666)
# Fix with:
sudo chmod 666 /var/log/locker.log

Locked Out — Switch Back to Permissive

If you're locked out and need to restore services, edit the config directly (requires physical access):

sudo nano /etc/locker/config.json
# Change "mode": "enforcing" to "mode": "permissive"
sudo systemctl restart locker

Key Design Decisions

CLI ↔ Service Communication

The CLI and service communicate through the shared configuration file at /etc/locker/config.json. The CLI writes configuration changes, and the service re-reads the file on every monitoring cycle (default: every 5 seconds). There is no direct IPC between the two.

Logging Architecture

Both the service (locker logger) and the CLI (locker.cli logger) write to the same log file at /var/log/locker.log. The file is created with 666 permissions so both root (service) and non-root (CLI) processes can write to it. This provides a unified audit trail.

Connected Serials File

The file /etc/locker/connect_android_serials.json allows simulating a connected device for testing and demos. When no real USB device is detected, the service checks this file as a fallback. If it exists, is valid JSON, contains an android_serial key, and the value matches the configured serial, the device is treated as connected.

Systemd Integration

The service runs as a Type=notify systemd unit. It sends READY=1 via the NOTIFY_SOCKET when initialization is complete. The --daemon flag is not used with systemd — systemd manages the process lifecycle directly.

Architecture

Locker consists of two main components: a background service daemon and a command-line interface.

System Overview


  +------------------+       +-------------------------+       +------------------+
  |                  |       |                         |       |                  |
  |   locker (CLI)   | ----> | /etc/locker/config.json | <---- |  lockerd (daemon)|
  |                  |       |                         |       |                  |
  +------------------+       +-------------------------+       +------------------+
         |                                                            |
         |                   +-------------------------+              |
         +-----------------> | /var/log/locker.log     | <------------+
                             | (unified audit log)     |
                             +-------------------------+
                                                                      |
                                                               +------+------+
                                                               |             |
                                                        USB check    File check
                                                               |             |
                                                        +------+    +-------+----------+
                                                        | udev |    | connect_android_ |
                                                        +------+    | serials.json     |
                                                                     +-----------------+

Service Daemon (lockerd)

The daemon runs a continuous monitoring loop:

  1. Load config — Re-reads /etc/locker/config.json on every cycle
  2. Check device — Looks for the configured Android serial via USB (pyudev), then falls back to checking connect_android_serials.json
  3. Act — If the device is connected, starts managed services. If disconnected, stops them (in enforcing mode)
  4. Sleep — Waits check_interval_seconds (default: 5) before the next cycle

Locking & Unlocking

In enforcing mode:

  • Device disconnected → All managed services are stopped via systemctl stop
  • Device connected → All managed services are started via systemctl start

In permissive mode, the same checks run and are logged, but no services are actually started or stopped.

Idempotent Operations

The service checks the current state before acting. If a service is already stopped (during lock) or already running (during unlock), it is skipped. This prevents unnecessary systemctl calls and noisy logs.

CLI (locker)

The CLI is a stateless tool that reads/writes the configuration file and queries system state. It does not communicate with the daemon directly. Key behaviors:

  • Read operations (list-services, get-android-serial, logs) do not require root
  • Write operations (add-service, set-mode, set-android-serial) require root to write to /etc/locker/config.json
  • All CLI operations are logged to /var/log/locker.log as an audit trail

Configuration Flow

User runs:   sudo locker add-service ssh
                    |
                    v
CLI writes:  /etc/locker/config.json  (adds "ssh" to services list)
CLI logs:    /var/log/locker.log      ("CLI: Executing command: add-service ssh")
                    |
                    v
Daemon reads config on next cycle (within 5 seconds)
                    |
                    v
Daemon acts: checks device, starts/stops ssh based on connection status

File Permissions

File Permissions Reason
/etc/locker/config.json 644 (root:root) Readable by all, writable by root (CLI requires sudo for writes)
/var/log/locker.log 666 (root:root) Writable by all so both the root daemon and non-root CLI can log
/etc/locker/connect_android_serials.json 644 (root:root) Optional file for testing; created/removed manually

Systemd Service Unit

[Unit]
Description=Lock-Down Service
After=network.target
Wants=network.target

[Service]
Type=notify
NotifyAccess=all
User=root
Group=root
ExecStart=/usr/bin/lockerd --config /etc/locker/config.json
ExecReload=/bin/kill -HUP $MAINPID
Restart=always
RestartSec=5
StandardOutput=journal
StandardError=journal
SyslogIdentifier=locker

# Security settings
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/etc/locker /var/log /var/run

[Install]
WantedBy=multi-user.target
